# SongHero plan83

Audit date: 2026-08-03

## Objective

Make SongHero safe to run on untrusted Spotify metadata, predictable for CLI
users, reproducible across runs, and capable of producing charts whose tick
timeline matches the audio. Keep the current Node CLI, Python analysis
pipeline, public-page metadata approach, playlist mode, Gemini enhancement,
lyrics fallback, and static landing page unless a finding below requires a
change.

## Current assessment

SongHero has a useful end-to-end prototype with a clear product shape:

- Spotify track and playlist inputs are supported without a Spotify API key.
- The pipeline has audio download, librosa analysis, optional Gemini analysis,
  lyrics lookup, chart generation, packaging, and an interactive CLI.
- The sample output contains valid Ogg Opus audio and an MP4 video container.
- The chart generator already emits BOM and CRLF output, sorts event lines, and
  creates four difficulty tracks.

It is not release-ready yet. The main risks are command execution safety,
incorrect or silently ignored options, timing drift caused by two incompatible
time models, weak failure handling, and documentation that describes a
different product from the code.

Recommended product contract for implementation:

- `--video` explicitly opts into video download. `--no-video` remains
  supported. Audio-only is the default because video is large, slow, and more
  failure-prone.
- Gemini is enabled by default only when a key is available. Missing Gemini is a
  clear warning and a successful non-AI path, not a failure.
- Lyrics are optional and are never generated by Gemini. They come from a
  source adapter and are included only when timing quality passes validation.
- Every generated chart is deterministic for the same input, configuration, and
  pinned model response.

## Findings

### P0: fix before normal user testing

| ID | Area | Evidence | Impact |
| --- | --- | --- | --- |
| S1 | Shell injection | `index.js` builds `execSync()` strings with the Spotify URL, title, artist, audio path, and lyrics path. `lib/download.js` builds an `ffmpeg` shell command from a path derived from metadata. | A crafted URL or metadata value can execute shell syntax. This is also fragile for quotes, dollar signs, and backticks in legitimate names. |
| S2 | TLS | `python/spotify.py` and `python/playlist.py` replace the default HTTPS context with `_create_unverified_context`. | Metadata and playlist responses can be intercepted or modified. This also weakens the trust boundary for all scraped values. |
| S3 | Path safety | The final folder uses raw artist and title values. `sanitize()` is incomplete, can return an empty or colliding name, and is not applied to `outputPath`. Rewrite recursively removes that path. | Traversal, collisions, malformed paths, and accidental deletion of an unintended output folder are possible. |
| C1 | Video options are disconnected | `runPipeline()` receives `forceVideo` and `noVideo`, but calls `downloadSong()` without either value. The downloader always attempts a video download. | `--no-video` does not save time or bandwidth, and `--video` does not change behavior. The CLI contract is false. |
| C2 | Chart timing model | Notes, sections, and lyrics use global `time_to_tick()`, while `SyncTrack` is built from noisy per-beat rounded BPM values. A fixed `section intro` event is also inserted at tick 5760 regardless of the audio. | A chart can be structurally valid while playing notes at the wrong times. The observed sample has 224 tempo events and a synthetic intro section. |
| R1 | No automated regression suite | There is no npm test script, no Python test package, no network fixtures, no chart validator, and no end-to-end smoke test. | The current pipeline can regress without detection, especially around web-page changes, timing, and media formats. |

### P1: fix in the first implementation cycle

| ID | Area | Evidence | Impact |
| --- | --- | --- | --- |
| C3 | Reproducibility | `_section_rand()` uses Python `hash(pattern)`. The value changes between fresh processes. | The same song can receive a different chart on every invocation, making debugging and user comparisons unreliable. |
| C4 | Lyrics alignment | `sync_lyrics_to_sections()` searches from the same section index for every line of a repeated label, so it does not advance through repeated verse or chorus sections. `lyrics_scaled` is never set. | Plain fallback lyrics can be placed in the wrong section. Duration differences are reported or dropped rather than aligned with a measured offset and scale. |
| C5 | AI validation | The prompt does not declare the `fret_mapping` field consumed by code. Fret weights are not required to have five positive finite values. A zero-sum response causes division by zero. Section indices, labels, and energy types are weakly validated. | A valid HTTP response can still crash chart generation or silently fall back to malformed musical parameters. |
| C6 | Audio edge cases | `beat_times[-1]` is read without checking for an empty beat result. Duration and tempo are not validated before division. | Silence, very short audio, decode failures, or unusual recordings can crash instead of returning an actionable error. |
| C7 | Media integrity | Video process exit codes and spawn errors are ignored. A non-MP4 video can be renamed to `.mp4` without remuxing or transcoding. The audio and video searches can resolve to different YouTube results. | Failed or incompatible media can be packaged as if successful. Users may get the wrong song or a video that Clone Hero cannot decode. |
| R2 | Failure cleanup and atomic output | Work directories are fixed under the repository, keyed only by artist and title, and are not removed on every failure. Packaging copies files directly into the final folder. | Retries can see stale artifacts, concurrent runs can collide, and interrupted packaging leaves partially usable charts. |
| R3 | Playlist result handling | A playlist prints `Playlist complete` regardless of per-track failures and does not return a failure status or summary. Rate-limit input accepts `NaN`. | Batch automation cannot tell whether the playlist succeeded, partially failed, or did nothing. |
| R4 | Metadata adapters | Spotify and playlist IDs are extracted with broad regexes. HTML is parsed with regexes and brittle first/last-brace JSON slicing. There is no size limit, cache, status handling, fixture coverage, or resilient fallback. | A small upstream page change can break every input. HTML entities, quotes, duplicate tracks, blank IDs, and partial playlist data are not handled consistently. |
| R5 | Dependency and environment checks | There is no preflight for Node, Python imports, `yt-dlp`, `ffmpeg`, writable output, or supported versions. The install script tries `brew` on Linux after warning that Homebrew is absent. | New users receive late and opaque failures. Linux installation is not actually supported by the documented script. |
| C8 | Chart serialization | Metadata is inserted into `.chart` and `song.ini` without a shared escaping routine. Event and note fields are not validated before writing. `lyrics.json` is described as final output but is not copied into the final package. | Names containing quotes or control characters can corrupt files. Invalid notes can reach Clone Hero, and the output contract is inconsistent. |

## Implementation plan

### Phase 0: freeze the behavior contract and fixtures

Create a small offline fixture set before refactoring behavior:

1. Add `test/fixtures/spotify-track.html` and `test/fixtures/spotify-playlist.html`
   with entities, escaped characters, duplicate tracks, and a blank item.
2. Add LRC fixtures for normal timing, multiple timestamps on one line, an
   offset tag, and a duration mismatch.
3. Add a short WAV or generated fixture that is safe to distribute, plus a
   checked-in expected analysis summary rather than a large media artifact.
4. Add a small hand-authored `.chart` fixture and a parser/validator that can
   inspect generated charts without launching Clone Hero.
5. Record the CLI contract in one place: accepted URL forms, defaults, video
   mode, Gemini behavior, lyrics behavior, output layout, exit codes, and
   playlist summary semantics.

Definition of done: tests can run offline and fail on the current known issues,
especially ignored video flags, nondeterminism, invalid AI weights, lyric
section advancement, malformed metadata, and invalid chart fields.

### Phase 1: harden the CLI and pipeline boundary

Refactor the orchestration before changing audio heuristics.

1. Add a `runProcess()` helper in a new `lib/process.js` using `spawn` or
   `execFile`, argument arrays, explicit environment, timeout, signal handling,
   bounded stdout/stderr, and captured exit codes. Do not use shell strings for
   user or metadata values.
2. Replace every dynamic `execSync()` call in `index.js` with that helper:
   Spotify resolver, lyrics resolver, analyzer, and chart generator.
3. Pass options as explicit objects. Use a single `videoMode` enum with
   `off`, `auto`, and `force`, then document the recommended default `off`.
   Validate `--rate-limit`, `--output`, URLs, and all option values. Reject
   unknown flags instead of silently ignoring them.
4. Move configuration and defaults into `lib/config.js`. Load dotenv quietly,
   avoid a module-level stale Gemini key, and make environment precedence
   explicit.
5. Add `lib/paths.js` with a stable slug based on the Spotify track ID plus a
   display name. Resolve the output root, prevent the generated child path from
   escaping it, and handle empty, reserved, or colliding names.
6. Use `fs.mkdtemp()` under the OS temp directory for each run. Put a run ID in
   logs. Always clean it in `finally` unless an explicit debug flag is set.
7. Package into a staging directory, validate the complete manifest, then rename
   the staging directory into the final output. Never recursively delete a path
   until it has been resolved and confirmed to be a generated child of the
   selected output root.
8. Return a typed result from `runPipeline()` with status, output path, stages,
   warnings, and error code. Make playlist mode aggregate success, skipped, and
   failed tracks and exit nonzero for any failure unless an explicit
   best-effort flag is supplied.
9. Add preflight checks for Python, required imports, `yt-dlp`, `ffmpeg`, output
   writability, and optional Gemini configuration. Give each failure a repair
   command.

Definition of done: malicious-looking titles and URLs are passed as data, not
shell syntax; failures have nonzero status; retries do not reuse stale data;
and a failed package leaves no final folder.

### Phase 2: make downloads correct and explicit

1. Split `lib/download.js` into audio and video responsibilities, or expose a
   `downloadSong({artist, title, outputDir, videoMode, cookies})` contract that
   makes the mode impossible to omit.
2. Download or inspect metadata for one candidate first. Score candidates by
   title, artist, duration, and official-channel signals. Use the selected URL
   for both audio and video so they cannot silently come from different search
   results.
3. Keep cookie use opt-in with a named browser option. Try public access first,
   and report cookie extraction failures without retrying the same impossible
   path.
4. Check `spawn` errors and close codes. Capture bounded stderr. Classify retryable
   network failures separately from missing formats, blocked content, and local
   dependency failures.
5. Use an explicit audio format and verify the result with `ffprobe`: container,
   codec, duration, and nonzero stream count. Use safe process arguments for any
   ffmpeg remux.
6. For video, select a supported format, enforce size and duration limits, and
   either preserve a tested codec/container or transcode to a documented
   compatibility target such as H.264/yuv420p MP4. Never change an extension
   without a matching remux or transcode.
7. Validate downloaded duration against Spotify metadata with a tolerance. Warn
   and require an explicit override for a large mismatch.

Definition of done: `--no-video` performs no video network request, `--video`
does, failed video does not invalidate a good audio chart unless forced mode is
used, and every packaged media file passes an integrity check.

### Phase 3: establish one canonical audio timeline

This is the most important chart-quality change.

1. Remove the duplicate `time_to_tick()` definition in `python/analyze.py`.
   Define one timeline module with `seconds_to_ticks()` and `ticks_to_seconds()`
   that accepts a canonical tempo map.
2. Keep detected beat times in seconds as the source observation. Fit a stable
   tempo map by smoothing beat intervals and merging changes that are likely
   detection jitter. Do not emit one tempo event for every rounded beat.
3. Make the tempo map begin at tick 0, use positive BPM values, and represent
   only persistent changes. Store the map in one unit, preferably BPM as a
   float internally and milli-BPM only at `.chart` serialization.
4. Convert notes, section events, lyric events, music start, and preview timing
   through the same integrated tempo map. Do not use the global tempo for some
   events and local tempo for others.
5. Remove the unconditional `section intro` event at tick 5760. Derive section
   events from detected sections, and add `music_start` only when the measured
   audio onset requires it.
6. Add timeline assertions: sorted beat times, nonnegative ticks, monotonic
   conversions, bounded round-trip error, and no note beyond the audio duration.
7. Handle no-beat, zero-duration, very short, and decode-error inputs with a
   controlled fallback or a clear error.

Definition of done: a golden fixture produces byte-identical analysis and chart
files across separate processes; the generated tempo map is compact; and
seconds-to-ticks round trips stay within a defined tolerance across every
tempo segment.

### Phase 4: improve note, section, lyric, and AI quality

#### Deterministic note generation

1. Replace Python `hash()` in `_section_rand()` with a stable digest such as
   `hashlib.blake2b` over pattern, beat index, seed, and an explicit generator
   version.
2. Validate fret ranges, duplicate `(tick, fret)` pairs, sustain lengths, and
   chord shape constraints before serialization.
3. Define difficulty invariants in code and tests: Easy has no orange and the
   lowest density, Medium has no orange, Hard may add orange and chords, and
   Expert is at least as dense as Hard. Avoid converting every note in a chord
   to orange during Hard upgrades.
4. Make the advertised density a measured target, not a documentation-only
   percentage. Report actual note density and chord rate in `analysis.json`.

#### Section detection

1. Use windowed energy and novelty features with beat-aligned boundaries rather
   than splitting on single RMS samples. Preserve minimum and maximum section
   lengths.
2. Keep labels within the supported vocabulary and distinguish a quiet intro
   from a quiet bridge or breakdown. Retain raw confidence and feature values
   for debugging.
3. Use repeat similarity only as a hint. Do not let an AI response create a
   pattern link unless the referenced section index is valid.

#### Lyrics

1. Parse all timestamps on an LRC line, handle common `[offset:]` metadata, and
   discard invalid or negative events.
2. When a lyric source duration differs from audio, estimate an offset and
   scale only inside safe thresholds. Record `lyrics_scaled`, `lyrics_offset`,
   and a confidence value. Drop lyrics with an explicit reason when confidence
   is too low.
3. Rewrite plain-text distribution as a sequential section allocator. Track the
   current section occurrence, not only the label, so repeated verses and
   choruses advance correctly. Add fixtures for repeated labels.
4. Keep lyric fetching source-based. Do not claim that Gemini creates lyrics or
   fills missing words.

#### Gemini

1. Put the model name in configuration, with a tested default and a clear
   fallback list. Keep model-specific behavior out of chart serialization.
2. Send the API key through the supported header mechanism rather than a URL
   query string. Keep timeout, retry, and rate-limit behavior explicit.
3. Define and validate a strict response schema: five finite positive fret
   weights, known styles, valid section indices, integer energy 1 through 10,
   and safe defaults for missing optional values. Reject zero-sum weights.
4. Add prompt and response fixtures for fenced JSON, extra prose, invalid JSON,
   missing fields, and valid partial responses.
5. Log AI usage as a stage result without printing secrets or full prompts that
   contain user metadata unnecessarily.

Definition of done: malformed AI output never crashes a run, no lyrics are
invented, repeated sections and lyric lines map predictably, and the same input
with the same AI response produces the same notes.

### Phase 5: validate charts and add regression coverage

Add tests at three levels:

1. Node unit tests using the built-in `node:test` runner for argument parsing,
   path slugs, output-root guards, process failures, option propagation, and
   playlist aggregation.
2. Python `unittest` tests for metadata fixtures, LRC parsing, timeline
   conversion, deterministic generation, AI schema validation, section mapping,
   and chart serialization.
3. An offline integration test that runs the pipeline with fake resolver,
   downloader, and AI responses. It should verify the final manifest and clean
   temp directory behavior without network access.

Add chart validation rules:

- BOM and line endings match the chosen Clone Hero compatibility target.
- Sync events are sorted, start at tick 0, and use valid positive BPM values.
- Event and note ticks are monotonic and nonnegative.
- Frets are 0 through 4, sustains are nonnegative, and duplicate fret notes at
  one tick are rejected.
- Every referenced media stream exists, has the expected codec/container, and
  has a duration within tolerance of the chart metadata.
- Difficulty tracks are present and meet the documented density invariants.

Add `npm test` as the single top-level test entry point. It should invoke the
Node and Python suites and return nonzero on any failure. Add a lightweight
GitHub Actions job for syntax checks, tests, fixture-based integration, and
installer linting. Keep network and large media tests out of the default CI
job.

Definition of done: a clean clone can run one documented test command and the
known current defects have permanent regression tests.

### Phase 6: synchronize installation, docs, and landing page

1. Rewrite README from the actual CLI contract. Include `npm install`, Python
   virtual environment setup, required system tools, `songhero --help`, track
   and playlist examples, defaults, output manifest, exit codes, troubleshooting,
   and responsible-use guidance.
2. Add `requirements.txt` and a development requirements file with supported
   version ranges. Avoid relying on globally installed Python packages.
3. Update `landing/install.sh` to use a venv, install Node dependencies, check
   commands before use, and handle macOS and Linux branches independently. Do
   not run `brew install` on Linux. Make shell profile edits opt-in and print
   exactly what changed.
4. Fix the landing page curl URL to the repository's real installer. Update
   flags and claims for video, lyrics, Gemini, dependencies, and final files.
   Remove the `google-generativeai` prerequisite if the implementation still
   uses HTTPS directly.
5. Add `rel="noopener noreferrer"` to external new-tab links, handle clipboard
   failure, and add a basic HTML/accessibility check. Consider a restrictive
   CSP and self-hosted fonts if the site remains public.
6. Add a privacy/terms/support section or linked pages that identify external
   services and state that users must have rights to downloaded content. Do not
   present this as legal advice.
7. Remove local Netlify state from version control if the deployment does not
   require it. Keep only portable deployment configuration.

Definition of done: every command shown on the landing page works from a clean
clone, and README, `--help`, installer, and landing copy agree.

### Phase 7: release and rollout

Use focused conventional commits in this order:

1. `test: add offline fixtures and chart validator`
2. `fix: harden subprocess, path, secret, and TLS handling`
3. `fix: honor media options and validate downloads`
4. `fix: canonicalize timing and lyric alignment`
5. `refactor: make analysis and AI output deterministic`
6. `docs: synchronize installer, README, and landing page`

Before release, run:

```bash
node --check index.js lib/*.js
python3 -m py_compile python/*.py
npm test
songhero --doctor
songhero -- generate <fixture-or-test-track> --no-gemini --no-lyrics --no-video
songhero -- playlist <fixture-playlist> --no-gemini --no-lyrics --no-video
```

For a manual media validation run, use a disposable output directory and verify
the result with `ffprobe`, the chart validator, and an actual Clone Hero scan.
Test one clean audio-only run, one video run, one skipped existing chart, one
rewrite, one failed track inside a playlist, and one title containing quotes,
parentheses, Unicode, and shell metacharacters.

Do not upload or publish a build until the following are true:

- No dynamic shell command remains in the pipeline.
- TLS certificate verification is enabled.
- Video mode is observable in downloader tests.
- Output is atomic and cleaned on failure.
- Analysis and chart generation are reproducible.
- The tempo map is compact and all event types share it.
- `npm test` passes from a clean checkout.
- README, installer, landing page, and `--help` are synchronized.

## Suggested implementation order for the first working slice

If the full plan must be staged, implement this minimum safe slice first:

1. Add fixtures and the test command.
2. Replace shell interpolation, remove TLS bypasses, validate paths, and add
   temp-directory cleanup.
3. Thread `videoMode` through the pipeline and check downloader exit codes.
4. Add chart validation and make the pipeline fail before final packaging when
   validation fails.
5. Replace the random hash and duplicate time conversion, then add the tempo
   map integration tests.
6. Fix repeated-section lyric allocation and AI weight validation.
7. Synchronize docs and installer only after the executable contract is stable.

This sequence puts security and silent data corruption ahead of cosmetic or
larger AI improvements while preserving a usable non-AI path at every step.

## Review addendum

This addendum records follow-up requirements from review. The original findings
and implementation phases remain unchanged.

### Contract decisions to make explicit

Record the complete option contract in one table before implementation:

| Mode | CLI mapping | Video request | Failure behavior |
| --- | --- | --- | --- |
| `off` | default, `--no-video` | Never | Continue with audio-only output |
| `auto` | Interactive `video auto` only, unless explicitly exposed as a flag | Best compatible candidate | Warn and continue when video is unavailable |
| `force` | `--video`, interactive `video on` or `video force` | Required | Fail the track if a compatible video cannot be packaged |

Reject conflicting `--video` and `--no-video` options. Define whether `force`
means only that video is required or also bypasses the non-music-video title
filter. Make command mode and legacy mode accept the same options, including
`--output`, `--rate-limit`, `--keep-temp`, and Gemini and lyrics toggles.

Define the following behaviors in the same contract:

1. Gemini with no key, an explicit `--gemini` with no key, and a failed model
   request.
2. Empty playlists, invalid tracks, duplicate tracks, skipped tracks, and
   best-effort playlist exit codes.
3. Whether an existing but invalid or partially written folder is skipped,
   repaired, or rejected.
4. The exact output manifest, including whether `lyrics.json`, analysis data,
   source URLs, and a SongHero ownership marker are public package files.

### Missing implementation work

Add concrete implementation items for findings that currently have tests or
recommendations but no code task:

1. Refactor the Spotify and playlist adapters to strictly parse accepted hosts,
   schemes, and 22-character track or playlist IDs. Use an HTML parser or an
   explicit entity decoder, handle attributes in either order, check status and
   content type, cap response bytes, and test redirects and malformed pages.
2. Apply response-size limits to lyrics and Gemini responses as well as Spotify
   pages. Bound `yt-dlp` stdout and stderr and terminate the child when a limit
   or timeout is reached.
3. Make browser cookie use opt-in with a named browser argument. Do not scan
   browser profiles by default. Store API keys with mode `0600`, prompt for a
   key without echo when practical, and never accept secrets as positional
   command-line arguments in documented workflows.
4. Pin the installer to a reviewed repository ref and define an integrity check
   for the downloaded installer or repository contents. Do not make a remote
   installer silently edit shell startup files or install a package manager.
5. If the installer creates a Python virtual environment, pass its interpreter
   path into the Node pipeline. Do not leave the runtime hard-coded to a
   potentially different system `python3`. Lock production Python dependency
   versions, not only broad version ranges.
6. Add dependency-injection seams for the process runner, metadata resolver,
   downloader, lyrics source, clock, and AI client. The offline integration
   tests should use those seams instead of relying on undocumented executable
   replacement or network interception.

### Reproducibility boundary

Define "same input" as a content-addressed input set, not merely a Spotify URL.
Record or cache the normalized Spotify metadata, selected media URL, downloaded
audio hash, lyrics response or source hash, generator version, configuration,
dependency lock, random seed, model name, and AI response hash. A live run may
change when external sources change, so document that limitation separately
from the deterministic offline guarantee.

The final manifest should expose enough non-secret provenance to reproduce or
diagnose a chart without storing API keys, browser cookies, or unnecessary full
prompts.

### Timeline verification requirements

The timeline definition of done must prove audio alignment, not only internal
consistency. Add deterministic fixtures for:

1. A constant-tempo click track.
2. A click track with a known tempo change.
3. Initial silence and a measured music onset.
4. Silence, zero-duration, very short, and decode-error inputs.

Assert expected click-to-note timing after `.chart` serialization. Use explicit
initial targets such as no more than one quantization tick for converter
round-trips and no more than 20 ms error on synthetic click-track events, then
adjust only with documented evidence. Test sustain ends as well as note starts.

The tempo-map implementation must specify how beat observations become chart
ticks, how tempo changes are placed at integer ticks, how rounding is handled,
and how Clone Hero interprets the resulting `SyncTrack`. A compact map and a
byte-identical wrong map are not sufficient acceptance criteria.

### Output safety and migration

Create the package staging directory under the selected output root so the
final rename cannot cross filesystems. Preserve the previous valid package
until a rewrite has fully validated the replacement, and provide rollback
behavior if the final rename fails.

Use an ownership marker or manifest before deleting an existing directory.
Never treat path containment alone as proof that an arbitrary existing folder
is safe to remove. Resolve and reject symlinked output roots or destinations
unless their behavior is explicitly supported.

Because the proposed ID-based slug changes the current folder layout, define a
migration policy for existing artist/title folders. Include tests for path
collisions, Unicode, empty names, reserved names, separators, symlinks, and
folders that are not SongHero-owned.

### AI schema correction

Choose one explicit schema for each AI-controlled value. If both fields are
needed, document and validate them separately:

- `fret_emphasis`: exactly five finite nonnegative numbers with a positive sum,
  normalized by the application.
- `fret_mapping`: an optional object mapping pitch classes `0` through `11` to
  integer frets `0` through `4`.
- `sections`: only integer section keys in range, supported labels and styles,
  finite integer energy from 1 through 10, and `identical_to` as a valid,
  non-self section index or null.

Delimit song metadata as untrusted context in the prompt. Add fixtures for
missing fields, extra fields, non-finite numbers, zero and negative weights,
integer-versus-string references, self-references, out-of-range references,
and prompt-injection-looking titles.

### Test and release corrections

Add automated tests for process timeout and spawn errors, SIGINT cleanup,
output-root and symlink guards, invalid existing packages, response-size
limits, secret redaction, option parity, and shell-metacharacter metadata.
Make the chart validator check the exact selected line-ending policy, including
the final newline, nondecreasing rather than strictly increasing event ticks,
tempo event uniqueness at tick zero, sustain ends, chart metadata escaping,
and the relationship between `song.ini`, `.chart`, and media files.
